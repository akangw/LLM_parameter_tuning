## Rules

1. **Decide per tag value: does it apply?** For every tag value in every dimension, independently judge whether this parameter is relevant to someone who cares about that tag value. A value applies if the parameter matters to deployments that match that tag.

2. **Default assumptions differ by dimension type.** Some dimensions describe "what environment this parameter operates in" (`model`, `hardware`, `deploy_topology`). For these, the default is that the parameter applies to ALL values unless the YAML shows a restriction. For example, if the parameter YAML says nothing about specific hardware, it applies to both A2 and A3 — use `hardware: [a2, a3]`. Some dimensions describe "what goal this parameter helps achieve" (`optimize_target`, `deploy_scenario`). For these, the default is that NO value applies unless the YAML shows the parameter actively helps with that goal. For example, a system library path does not help optimize TTFT — leave it out.

3. **Multiple values can apply.** A parameter may affect multiple optimization targets, work on multiple hardware types, or be relevant to multiple deployment scenarios. List all that apply.

4. **Only use exact values from the tag schema — never invent new values.** Each dimension's allowed values are listed in the tag schema above. You MUST NOT output any value that is not in that list, even if the parameter's YAML uses similar terminology. For example, `performance_scope` in the parameter YAML may contain "latency" — this is NOT a valid optimize_target value. Map "latency" to `ttft` (if prefill-focused) or `tpot` (if decode-focused), never output "latency".

5. **Use `[]` for optimize_target or deploy_scenario when the parameter doesn't actively help achieve any specific goal in that dimension.** This is common for infrastructural parameters (library paths, compiler settings, device visibility). For `model`, `hardware`, and `deploy_topology`, `[]` should be rare — only use it when the parameter is truly irrelevant to all values (which is unusual).

6. **Base your judgment on the full YAML content.** The fields `impact_detail`, `constraints`, `tuning_advice`, `usage_locations`, `related_parameters`, and `performance_scope` provide the strongest signals. Use signals in the tag schema as clues, not rigid rules.

7. **Every dimension listed in the tag schema MUST appear in your output.** Do not omit any dimension, even if its value is `[]`.

## Output format

Output ONLY raw YAML — no markdown fences, no introductory or concluding text. Use this structure:

```yaml
tags:
  <dimension_name>: [value1, value2]
  <dimension_name>: []
  ...
```

Include ALL dimensions from the tag schema. Use `[]` for dimensions where no value applies.
